## 0. 先确认你到底是哪一种角色

这决定 MVP 的重心，建议先想清楚：

| 角色 | 核心痛点 | 系统重心 |
|---|---|---|
| A. 个人执行者 | 事多、插单多、不知道先做哪个、汇报烦 | 收件箱、今日排期、延期、日报 |
| B. 项目经理 | 多项目并行、里程碑、依赖、风险、干系人 | 项目组合、里程碑、RAID、风险登记册 |
| C. 两者都是 | 既要自己干，又要对项目结果负责 | A 的全部 + B 的轻量版 |

下面方案默认按 **C（偏 A）** 设计：先把个人闭环跑通，再逐步加项目组合能力。如果你主要是 B，第 3 节的数据模型和第 5 节界面需要加权重。

## 1. 场景拆解：一条任务从进入到产生价值

```text
捕获 Capture
  ↓  原始文本 / 语音 / 截图 / 会议纪要 / 邮件
结构化 Parse
  ↓  AI 草稿：项目、类型、截止、估算、优先级、子任务
确认 Confirm
  ↓  人只做"改一两个字段 + 确认"，不填表
排期 Plan
  ↓  产能校验：今天到底放不放得下
执行 Execute
  ↓  计时、状态流转、阻塞/等待记录
交付 Deliver
  ↓  完成 ≠ 交付 ≠ 验收，分别打时间戳
汇报 Report
  ↓  日报 / 周报 / 项目状态 / 风险分析
复盘 Review
  ↓  估算偏差、延期原因、时间去向
画像 Profile
  ↓  用真实事件反推工作习惯，指导下周排期
```

**每一步的失败点：**

| 阶段 | 常见失败 | 后果 |
|---|---|---|
| 捕获 | 要打开软件、填很多字段 | 干脆不记，靠脑子 |
| 结构化 | AI 乱归类、乱编截止时间 | 不信任，弃用 |
| 确认 | 每次都要手填 | 摩擦大于收益 |
| 排期 | 只列清单，不算产能 | 每天都排满，天天延期 |
| 执行 | 没有实际耗时 | 估算永远不准 |
| 交付 | 把"做完"当"交付" | 完成率虚高，老板视角失真 |
| 汇报 | 从零回忆 | 日报半小时，周报两小时 |
| 复盘 | 只看到红色延期 | 焦虑，但不知道改什么 |
| 画像 | 变成 KPI 考核 | 自我否定，或数据造假 |

## 2. 你还需要补充的 13 个关键设计

### 2.1 统一收件箱：捕获必须先于整理

- 全局快捷键（如 `Ctrl+Space`）唤起一个只有一行的输入框，粘贴原文即可。
- 支持来源：手动输入、微信/飞书/钉钉复制、邮件转发、会议纪要、截图 OCR（后期）。
- **原始文本必须原样保留**（`raw_input` / `source_ref`），AI 只生成"草稿"，永远可回溯。
- 默认落到 `inbox` 状态，不直接进项目；确认后才成为正式任务。
- 目标：**从按快捷键到确认，≤ 20 秒**。

> 关键原则：捕获时不做分类，分类时不做录入。把两件事拆开，摩擦才会低。

### 2.2 项目注册表 + 分类学习闭环

AI 分类准不准，80% 取决于你有没有一份好的"项目字典"，而不是模型多强。

每个项目至少维护：

- 项目名、代号、常用别名（如"星火""XH""老板那个新业务"）
- 一句话目标
- 关键交付物（文档、系统、活动、报告……）
- 干系人（谁提需求、谁验收）
- 起止时间、当前里程碑
- 5～10 个典型任务关键词

分类策略（个人规模 < 100 个项目，不需要向量数据库）：

1. 规则优先：项目名/别名/代号精确命中 → 高置信度。
2. LLM 从候选清单里选，**只允许选候选或 `unknown`**，并输出置信度和第二候选。
3. 置信度 < 0.7，或第一、第二候选差距 < 0.15 → **必须问你**："这是星火项目还是内部工具？"
4. 你的每次纠正，自动写回 `project_alias` 和 few-shot 示例。
5. 每周统计 top-1 准确率，低于 85% 就补项目字典，而不是换模型。

### 2.3 任务状态机：完成 ≠ 交付 ≠ 验收

这是最容易被忽略、但最影响数据可信度的一点。

```text
inbox → planned → doing → done → delivered → accepted
                    ↓
                 blocked / waiting
                    ↓
                cancelled
```

对应三个时间戳：

| 字段 | 含义 | 用途 |
|---|---|---|
| `completed_at` | 我这边做完了 | 个人产出统计 |
| `delivered_at` | 已发给老板/客户/下游 | 交付周期 |
| `accepted_at` | 对方确认可用 | 真正闭环 |

如果只记"完成"，你会得到虚高的完成率，也会漏掉"发出去一周没人验收"这种真实风险。

另外补两个字段：

- `waiting_on`：在等谁/等什么（人等、审批、环境、数据）。
- `reason_code`：延期或取消的原因码（估算错、被插队、等他人、需求变更、自己拖延、优先级调整）。

### 2.4 估算要带区间，并且会自我校准

不要给一个假装精确的"2 小时"，给一个区间，并说明依据。

冷启动：

- 用历史相似任务的**实际耗时**做基准（同类型 + 文本相似 top 10）。
- 没有历史时，用同类型任务中位数；再没有，才让 LLM 估。
- 输出 `P50`（一半概率能完成）和 `P90`（比较稳妥）。

校准（关键）：

```text
个人偏差系数 bias_type = (Σ 实际耗时 + 4 × 1.0) / (Σ 预估耗时 + 4)
```

- 按任务类型分别算（写方案、写代码、开会、分析、行政、沟通）。
- 先验权重 4 次，避免前几单波动过大；结果限制在 0.5～3.0。
- 展示时写成："预计 2h；按你过去 12 个同类任务，通常要多 35%，实际预留 2.7h。"

每次完成后自动更新系数，月底看一张"预估 vs 实际"散点图。**估算能力是这套系统最长期的价值之一。**

### 2.5 产能与 WIP：系统要敢说"今天放不下"

只列待办的系统都会失败，因为它不承认你一天只有那么多小时。

- 每日可用工时 = 工作时长 − 会议 − 15% 缓冲。
- 当日负载 = 计划任务的 `P50` 之和 + 临期任务分摊。
- 负载 > 90% 可用 → 黄色警告；> 110% → 红色，必须做取舍。
- 进行中任务（`doing`）建议上限 3 个，超过就提示"先收口"。
- 系统给出**可执行的取舍建议**，而不是只说"你超载了"：

> 今天 3 件事合计 9.5h，可用 6h。建议：A 上午做（3h），B 拆成"先出提纲"（1h）今天交付，C 延到周四。需要我生成一段跟老板沟通的话术吗？

这就是这套系统相对普通 Todo 的核心差异：**它帮你做承诺管理，而不是帮你堆任务。**

### 2.6 延期处理：要原因码，不要红色感叹号

延期不是一种问题，而是五种问题：

| 原因码 | 对策 |
|---|---|
| `estimate_wrong` | 修正估算系数、拆分任务 |
| `interrupted` | 设保护时间、减少插单 |
| `waiting` | 催办、升级、换路径 |
| `scope_change` | 记录变更、重谈范围和时间 |
| `procrastination` | 拆小、降低启动成本、换时段 |
| `priority_change` | 明确取舍，更新承诺 |

提醒节奏建议：

- 到期前 1 天：轻提醒。
- 到期当天 09:00：进入今日必做。
- 逾期 +1 天：单独列出，要求选"今天做/改期/取消/找人"。
- 逾期 +3 天、+7 天：升级提醒，并自动生成风险候选。
- 禁止每几个小时弹一次；同一天同一任务最多提醒 2 次。
- 允许 snooze，但必须选原因；同一任务 snooze 超过 2 次，强制做决定。

### 2.7 等待、依赖、阻塞：隐性延期的最大来源

- 任务可以标记 `waiting_on`（人/审批/环境/数据）。
- 记录"从什么时候开始等"，超过 2 天自动进入跟进清单。
- 同一人身上等待超过 3 项 → 升级为"单点依赖风险"。
- 任务之间建依赖关系（`depends_on`），前置未完成时，后续任务不进入"今天可做"。
- 每周统计"等待他人"占总时间的比例，这是你个人产能之外的系统性损耗。

### 2.8 承诺管理与"老板视角"

老板给你安排任务时，真正要管的是三件事：

1. **你承诺了什么**（范围 + 时间 + 交付物）
2. **你有没有兑现**（承诺兑现率）
3. **兑现不了时，你有没有提前说**

建议加两个字段：`promised_at`、`promised_to`。系统自动对比"承诺时间 vs 实际交付时间"，生成：

- 承诺兑现率
- 平均提前/延迟天数
- 需要提前预警的任务（预计完成时间 > 承诺时间）

当产能不足时，一键生成沟通话术（可直接复制到 IM）：

> 王总，今天您安排的 A、B、C 三件，我排了一下：A 需要 3h、B 需要 4h、C 需要 2.5h，合计 9.5h，今天可用约 6h。建议 A 今天完成，B 先出第一版框架周四给完整版，C 顺延到周五。您看这个优先级可以吗？

### 2.9 报告生成：事实层与叙述层必须分离

不要让 LLM 直接"回忆"你干了什么，它一定会编。

正确做法：

```text
SQL 计算事实 → 冻结成 facts.json（带 hash）
        ↓
LLM 只负责把事实写成通顺的叙述
        ↓
每条结论必须能引用 task_id
        ↓
你编辑 → 导出 / 复制
```

日报模板（建议 5 块，控制在 300 字内）：

```markdown
## 今日完成
- [星火项目] 完成接口联调，输出测试报告（3.5h）#T1024

## 进行中
- [内部工具] 权限模块 60%，下一步接 SSO，预计周四完成

## 阻塞 / 等待
- 等运维开通测试库（已等 2 天，影响联调）

## 明日计划
1. 星火：修复联调问题（2h）
2. 内部工具：SSO 对接（4h）

## 需要决策 / 风险
- 测试库若周三仍不可用，周五上线有风险，需提前准备回滚方案
```

周报模板：

- 项目健康总览（绿/黄/红 + 一句话原因）
- 本周产出（按项目分组）
- 计划 vs 实际（完成率、估算偏差）
- 延期与原因分布
- 风险 Top 3 + 缓解措施
- 下周计划与资源需求
- 时间分配（项目 / 类型 / 会议占比）

导出格式：Markdown、DOCX、XLSX、PDF；另外提供"复制为 IM 纯文本"。

### 2.10 风险分析：规则引擎负责发现，LLM 负责解释

风险不要靠 LLM 凭空想，先用规则算指标：

| 规则 | 阈值 | 风险等级 |
|---|---|---|
| 里程碑 7 天内且完成度 < 50% | 触发 | 高 |
| 单任务延期 > 3 天 | 触发 | 中 |
| 阻塞 > 2 天 | 触发 | 中/高 |
| 同一项目进行中任务 > 5 | 触发 | 中 |
| 本周需求变更 ≥ 2 次 | 触发 | 中 |
| 本周超载天数 ≥ 2 | 触发 | 高（个人产能） |
| 老板插单占比 > 30% | 触发 | 中（流程风险） |
| 同一干系人等待任务 > 3 | 触发 | 高 |

然后让 LLM 基于这些事实输出：风险描述、可能影响、建议动作、需要谁支持。最后进入**风险登记册**：

| 字段 | 说明 |
|---|---|
| 类别 | 进度/范围/资源/依赖/质量/干系人/个人产能 |
| 概率 × 影响 | 1～5 分，得出分数 |
| 状态 | open / mitigating / closed / accepted |
| 缓解措施 | 具体动作，不写"加强沟通" |
| 负责人 | 你或他人 |
| 复核日期 | 每周复盘 |

风险要留历史快照，才能看趋势：这周比上周更危险，还是只是你记录得更多？

### 2.11 个人画像：可解释、非评判、可关闭

画像的价值是"照镜子"，不是"打 KPI"。建议 6 个维度：

| 维度 | 指标示例 | 数据来源 |
|---|---|---|
| 执行力 | 按时完成率、平均延期天数、WIP 峰值 | task / status_event |
| 估算力 | P50 误差、按类型的偏差系数 | estimate vs actual |
| 节奏 | 深度工作块（≥50min）数量、高效时段、上下文切换 | time_entry |
| 结构 | 项目/类型分布、紧急×重要四象限、插单占比 | task |
| 协作 | Top 协作对象、等待他人时长、跟进延迟 | waiting_on / person |
| 成长 | 新增技能标签、任务复杂度趋势、复盘主题 | tag / document |
| 可持续 | 加班天数、周末工作、连续超载 | time_entry / calendar |

展示原则：

- 雷达图对比的是**你自己的过去 8 周**，不是同事。
- 每个分数都能点开看原始事件（哪几天、哪些任务）。
- 样本不足时显示"数据不足"，不要硬算。
- 默认只对自己可见；导出时支持脱敏。
- 语言用描述，不用评价："你周三上午完成深度任务的成功率最高"，而不是"你的效率只有 62 分"。
- 每月给 3 条发现 + 3 个可执行实验，不要给一堆图表。

> 建议先做一个**静态画像 Demo**（假数据 + 真实视觉），确认你想要的呈现方式，再接真实数据。这样不会在数据管道上白花两周。

### 2.12 隐私、备份、审计、离线

工作内容大概率涉及公司信息，必须一开始就设计：

- **本地优先**：SQLite 存在本机，附件存本地目录，默认不上传。
- **模型可选**：云端 API（DeepSeek/OpenAI 兼容）或本地 Ollama；敏感任务强制走本地。
- **发送前脱敏**：人名 → 角色，客户名 → 客户 A，金额/合同号可屏蔽。
- **AI 操作日志**：每次调用记录输入 hash、输出、是否被采纳，支持一键撤销。
- **每日自动备份**：7 日 + 4 周 + 12 月轮转；支持一键导出全部 JSON/Markdown。
- **静态加密**：至少依赖 BitLocker；更高要求用 SQLCipher 或字段级加密。
- **无遥测**，不做账号体系，不默认云同步。

### 2.13 仪式与工具自身指标

工具不能只提供页面，要推动三个仪式：

| 仪式 | 时长 | 做什么 |
|---|---|---|
| 早规划 | 5 min | 看简报、定 1～3 件必做、确认产能 |
| 晚收尾 | 5 min | 标完成、记实际耗时、写日报、记阻塞 |
| 周复盘 | 20 min | 周报、延期原因、风险复核、下周计划 |

同时监控工具本身是否有效：

- 本周漏事数（到期前从未在任何简报中出现）
- 捕获→确认平均耗时
- 日报/周报生成耗时
- 分类 top-1 准确率
- 估算误差趋势
- 周复盘完成率

如果"记录负担 > 收益"，先砍字段，不要加功能。

## 3. 数据模型（SQLite）

### 3.1 最小可用表

```sql
-- 项目
CREATE TABLE project (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  code          TEXT,
  goal          TEXT,
  status        TEXT NOT NULL DEFAULT 'active',  -- active/paused/done/archived
  priority      INTEGER DEFAULT 3,               -- 1 最高
  owner         TEXT,
  start_date    TEXT,
  target_date   TEXT,
  health        TEXT DEFAULT 'green',            -- green/amber/red
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

-- 项目别名（分类的关键）
CREATE TABLE project_alias (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id  TEXT NOT NULL REFERENCES project(id),
  alias       TEXT NOT NULL,
  weight      REAL DEFAULT 1.0,
  source      TEXT DEFAULT 'manual'              -- manual/learned
);

-- 里程碑（项目经理模式需要）
CREATE TABLE milestone (
  id          TEXT PRIMARY KEY,
  project_id  TEXT NOT NULL REFERENCES project(id),
  name        TEXT NOT NULL,
  due_at      TEXT,
  status      TEXT DEFAULT 'open',               -- open/done/missed
  progress    INTEGER DEFAULT 0
);

-- 任务
CREATE TABLE task (
  id                TEXT PRIMARY KEY,
  project_id        TEXT REFERENCES project(id),
  parent_id         TEXT REFERENCES task(id),
  title             TEXT NOT NULL,
  description       TEXT,
  task_type         TEXT,                        -- writing/coding/analysis/meeting/admin/comms/design/other
  source            TEXT,                        -- boss/im/email/meeting/self
  source_ref        TEXT,                        -- 原始消息链接/截图路径
  raw_input         TEXT,                        -- 原始描述，永久保留
  requester         TEXT,
  status            TEXT NOT NULL DEFAULT 'inbox',
  priority          INTEGER DEFAULT 3,
  importance        INTEGER DEFAULT 3,
  progress          INTEGER DEFAULT 0,
  estimate_p50_min  INTEGER,
  estimate_p90_min  INTEGER,
  actual_min        INTEGER DEFAULT 0,
  due_at            TEXT,
  original_due_at   TEXT,
  planned_for       TEXT,                        -- YYYY-MM-DD
  promised_at       TEXT,
  promised_to       TEXT,
  started_at        TEXT,
  completed_at      TEXT,
  delivered_at      TEXT,
  accepted_at       TEXT,
  waiting_on        TEXT,
  block_reason      TEXT,
  reason_code       TEXT,                        -- estimate_wrong/interrupted/waiting/scope_change/procrastination/priority_change/other
```

### 3.3 核心指标口径

```text
按时完成率 = 有 due_at 且 completed_at <= due_at 的已完成任务 / 有 due_at 的已完成任务
平均延期天数 = avg(julianday(completed_at) - julianday(due_at))，仅延期任务
估算偏差 = median(actual_min / estimate_p50_min)，按 task_type 分组
承诺兑现率 = delivered_at <= promised_at 的任务 / 有 promised_at 的任务
深度工作块 = 单次 time_entry >= 50 分钟且无打断
上下文切换 = 2 小时内出现过的不同 project_id 数量
等待时长 = now - waiting_on 开始时间（或 status_event 中进入 waiting 的时间）
超载日 = 当日计划 P50 总和 > 可用工时的 110%
```

## 4. 核心流程设计

### 4.1 捕获 → 结构化

输入示例：

> 老板说：星火项目下周要给客户演示，你把这周的联调问题整理一下，周三前发我，顺便把演示环境也准备下。

AI 输出草稿（JSON）：

```json
{
  "title": "整理星火项目联调问题并发给老板",
  "project_guess": {
    "id": "p_xinghuo",
    "name": "星火项目",
    "confidence": 0.93,
    "alternatives": []
  },
  "task_type": "analysis",
  "source": "boss",
  "requester": "王总",
  "due_at": "2026-10-23T18:00:00+08:00",
  "estimate": {
    "p50_min": 120,
    "p90_min": 180,
    "basis": "过去 8 个同类问题整理任务中位数 110 分钟，个人偏差系数 1.15"
  },
  "priority": 1,
  "importance": 5,
  "subtasks": [
    { "title": "汇总本周联调问题", "estimate_p50_min": 60 },
    { "title": "准备演示环境", "estimate_p50_min": 60 }
  ],
  "missing_fields": [],
  "clarifying_question": null
}
```

规则：

- 截止时间不明确时，**不要编**，输出 `missing_fields: ["due_at"]` 和一句追问。
- 一句话包含多件事时，拆成子任务，但保留同一个父任务。
- 估算必须给依据；没有历史数据就标 `basis: "无历史数据，AI 粗估"`。
- 低置信度字段在 UI 上高亮，确认时优先让你改。

### 4.2 项目归属

```text
1. 别名/代号精确命中 → 直接建议，置信度 0.95
2. 候选清单 + few-shot 交给 LLM → 返回 id/confidence/alternative
3. 规则融合：
   final_conf = max(alias_conf, llm_conf)
   若 llm_top1 与 top2 差距 < 0.15 → 视为不确定
4. final_conf < 0.7 → 弹窗二选一/三选一（含 "新建项目" 和 "不属于任何项目"）
5. 用户选择 → 写入 project_alias（source=learned）+ ai_log(accepted=1)
```

候选清单 prompt 结构：

```text
你是项目归属分类器。只能从下面的候选项目中选择，或输出 unknown。
判断优先级：明确项目名/代号 > 交付物 > 请求人惯常负责的项目 > 近期上下文。

候选：
- p_xinghuo | 星火项目 | 目标：Q4 客户演示 | 别名：星火,XH,演示项目 | 近期任务：联调,演示环境,客户验收
- p_internal | 内部工具 | 目标：提升交付效率 | 别名：工具链,平台 | 近期任务：SSO,权限,部署

任务原文：...
```

### 4.3 时间估算

```text
候选集 = 同 task_type + 文本相似度 top 10 的已完成任务
若候选 >= 3：
    baseline = median(actual_min)
    p50 = baseline * bias_type
    p90 = quantile90(actual_min) * bias_type
否则若同类型任务 >= 5：
    baseline = median(同类型 actual_min)
否则：
    baseline = LLM 粗估（标记低置信度）

bias_type = (Σ actual + 4) / (Σ estimate + 4)，限制在 [0.5, 3.0]
```

UI 上永远显示区间 + 依据，不显示单一数字。

### 4.4 今日排期与超载处理

```text
available = 工作分钟 - 会议分钟 - 15% 缓冲
must      = 逾期 + 今天到期 + 老板 P1
should    = 本周到期 + 项目关键路径
could     = 其他

planned_load = Σ P50(must + should 中今天做的)
if planned_load > available * 1.1:
    按 priority_score 从低到高生成"建议延后"列表
    给出 2 套方案（保交付 / 保质量）
    可一键生成沟通话术
```

`priority_score` 要可解释，不要黑盒：

```text
score = 0.4 * 紧迫度 + 0.3 * 影响 + 0.2 * 老板/关键干系人 + 0.1 * 依赖下游数量
```

界面显示每一项的得分构成，允许手动覆盖。

### 4.5 提醒与升级

| 时间 | 动作 |
|---|---|
| 08:45 | 今日简报：必做 3 件、逾期、等待跟进、产能条 |
| 12:30 | 可选：上午进度检查（只在有逾期时） |
| 18:00 | 收尾：记录实际耗时、写日报、处理未完成 |
| 周五 16:30 | 周报 + 风险复核提醒 |
| 逾期 +1/+3/+7 天 | 分级升级，要求做决定 |

原则：**汇总提醒优先于单任务提醒；提醒的目的是让你做决定，不是让你焦虑。**

### 4.6 日报 / 周报生成

事实 JSON 示例：

```json
{
  "period": { "start": "2026-10-21", "end": "2026-10-21" },
  "completed": [
    {
      "task_id": "T1024",
      "title": "完成接口联调",
      "project": "星火项目",
      "actual_min": 210,
      "completed_at": "2026-10-21T17:20:00+08:00",
      "output": "测试报告 v2"
    }
  ],
  "in_progress": [],
  "blocked": [],
  "overdue": [],
  "time_by_project": { "星火项目": 210 },
  "risks": [],
  "next_plan": []
}
```

LLM 约束：

- 只能使用 facts 中的事实；不得补充未出现的人名、数字、结论。
- 每条完成项带 `task_id` 引用。
- 不确定就写"数据不足"。
- 输出 300 字以内叙述 + 结构化要点。
- 生成后必须由你确认才能导出。

### 4.7 风险分析

```text
规则引擎扫描 → 候选风险（含证据 task_id / 指标值）
      ↓
LLM 解释：为什么会发生、影响是什么、建议动作、需要谁支持
      ↓
你确认 → 进入风险登记册（概率/影响/负责人/复核日）
      ↓
每周快照 → 趋势
```

不要让 LLM 直接"阅读所有任务然后自由发挥"，那样既慢又不可复现。

### 4.8 画像计算

```text
事件表（task/status_event/time_entry）→ SQL 聚合 → 指标 JSON
      ↓
与个人过去 8 周基线比较 → 归一化 0-100
      ↓
LLM 只写解读（3 条发现 + 3 个实验），不改数字
      ↓
存入 profile_snapshot，按月对比
```

画像 Demo 建议先做 6 个卡片 + 1 个雷达 + 1 条趋势，不要一上来做 30 个图。

## 6. 技术选型

### 6.1 方案对比

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| **Electron + React + SQLite** | 生态成熟、桌面能力强（托盘/快捷键/通知/PDF）、纯 JS/TS | 安装包大（100MB+）、内存高 | 快速做出可用产品（推荐） |
| **Tauri 2 + React** | 包小、内存低、Rust 后端稳 | 需要 Rust + MSVC 构建工具、首次编译慢 | 长期维护、在意体积 |
| **本地 Web（FastAPI + React/PWA）** | 后端简单、Python 生态好、SQLite 原生 | 桌面集成弱（快捷键/托盘）、要开浏览器 | 先验证流程、自己用 |
| **低代码（飞书多维表格/Notion）** | 1～2 天上线、协作/移动端现成 | AI 分类和报告定制受限、数据在云端 | 先跑两周验证字段和仪式 |

> 你这台机器目前有 Node 24、npm、Python 3.12；**没有 Rust 和 Git**。所以：
> - 想最快出桌面版：选 Electron。
> - 想长期做得精致：先装 Rust + VS Build Tools，再上 Tauri。
> - 想两周内验证：先用飞书多维表格/Notion 跑流程，再决定是否自研。

### 6.3 架构分层

```text
┌──────────────── UI（React）────────────────┐
│ 今日 / 收件箱 / 项目 / 报表 / 画像 / 设置 │
└──────────────────┬─────────────────────────┘
                   │ IPC（preload 白名单）
┌──────────────────▼─────────────────────────┐
│ 主进程                                     │
│  ├─ 领域服务：任务状态机、排期、指标       │
│  ├─ AI 编排：解析/分类/估算/报告/风险      │
│  ├─ 调度器：提醒、日报、周报、备份         │
│  └─ 导出器：MD/DOCX/XLSX/PDF               │
└──────────────────┬─────────────────────────┘
                   │
┌──────────────────▼─────────────────────────┐
│ SQLite + 本地文件（附件/备份/日志）        │
└────────────────────────────────────────────┘
```

原则：

- AI 调用只在主进程，API Key 不进渲染进程。
- 领域逻辑与 UI 解耦，便于测试和以后换壳（Electron → Tauri）。
- 所有写操作走服务层，统一写 `status_event` 和 `updated_at`。

### 6.4 AI 调用策略

| 场景 | 模型 | 要求 |
|---|---|---|
| 捕获解析 | 便宜/快的小模型 | JSON Schema 结构化输出 |
| 项目分类 | 小模型 + 候选清单 | 低温度、必须给置信度 |
| 时间估算 | 代码算 + LLM 兜底 | 有历史时不让 LLM 编 |
| 日报/周报 | 中等模型 | 只基于 facts，引用 task_id |
| 风险解释 | 中等模型 | 输出结构化风险条目 |
| 画像解读 | 中等模型 | 只解读，不改数字 |

工程细节：

- 所有 prompt 版本化（`prompt_version` 存进 `ai_log`）。
- JSON 解析失败自动重试 1 次，再失败降级为手工表单。
- 记录 token 和耗时，方便控制成本。
- 敏感项目配置为"仅本地模型"。

- Electron + React + SQLite 初始化，迁移脚本。

### Phase 3：提醒与报告（第 3 周）

- 早简报、晚收尾、逾期升级、snooze 规则。

- 规则引擎 + 风险登记册 + 周趋势。

### Phase 5：试用与迭代（第 5～6 周）

- 连续用两周，记录：漏事数、日报耗时、估算误差、分类准确率。

- 再决定是否做：日历同步、IM 机器人、移动端捕获、DOCX/PDF 模板。

## 9. 失败模式与对策

| 失败模式 | 典型表现 | 对策 |
|---|---|---|
| 记录负担过重 | 用三天就放弃 | 默认值 + AI 填表 + 只保留 6 个必填字段 |
| 分类不可信 | 每次都归错，干脆不看 | 低置信度必问 + 一键纠正 + 别名学习 |
| 提醒疲劳 | 通知太多，全部忽略 | 每日 2 次汇总 + 分级升级 + snooze 限额 |
| 报告假大空 | "持续推进""加强协同" | facts 与叙述分离 + 强制引用 task_id |
| 排期失真 | 每天都排 10 小时 | 产能校验 + WIP 上限 + 强制取舍 |
| 画像变考核 | 焦虑、造假 | 只跟自己比 + 可隐藏 + 只给建议不给评分 |
| 隐私泄露 | 公司信息进了云端 | 本地优先 + 脱敏 + 项目级模型策略 |
| 数据丢失 | 换机/崩溃 | 每日备份 + 一键导出 + 版本化迁移 |
| 过度自动化 | AI 擅自改期/取消 | 关键动作必须人工确认 + 可撤销 |
| 范围蔓延 | 功能越做越多 | 每两周只允许加一个功能，且必须对应一个指标 |

## 10. 需要你确认的 6 个问题

1. **你的角色**：主要是被分配任务的执行者，还是要管多个项目和里程碑的项目经理？
2. **使用场景**：只在 Windows 单机用，还是需要手机快速捕获、多设备同步？
3. **数据敏感度**：任务内容能否发给云端大模型（DeepSeek/OpenAI），还是必须本地模型？
4. **现有工具**：公司是否在用 Jira/禅道/飞书项目/钉钉/企业微信？需要对接还是纯个人记录？大概多少个项目？
5. **技术偏好**：你希望我直接搭一个可运行的 Electron 桌面 App，还是先用飞书多维表格/Notion 跑两周验证？
6. **画像受众**：只给自己看，还是要导出给老板做汇报？这决定脱敏和叙事口径。
