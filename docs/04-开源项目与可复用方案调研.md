# 开源项目与可复用方案调研

> 调研日期：2026-10-21
> 说明：GitHub Marketplace 主要托管 GitHub Apps / Actions，不托管桌面软件；所以下面调研的是 **GitHub 仓库 / 开源项目**，以及可以直接复用的组件。
> 星标数为调研时 GitHub API 返回值，仅用于判断量级，会持续变化。

---

## 0. 结论先行

1. **不要 fork 一个完整的项目管理平台**（Plane / Huly / OpenProject / AppFlowy）。它们是多用户、云原生、重架构，许可证多为 AGPL/GPL，改造成本会吞掉 MVP 的时间。
2. **采用“薄桌面壳 + 本地 SQLite + 可插拔连接器 + AI 编排”的拼装式架构**。核心壁垒在“承诺/产能引擎、估时校准、事实型报告、可解释画像”，不在项目管理页面的 CRUD。
3. **两个最值得直接借力的开源项目**：
   - **ActivityWatch**：自动时间追踪、窗口/离开检测、本地优先。画像和节奏数据可以直接接它的 localhost API。
   - **Super Productivity**：时间盒、计时器、每日总结、Jira/GitHub 集成，是最接近“执行层”的成熟参考（MIT）。
4. **连接器不要一上来做几十个**。先做“手动捕获 + Excel/CSV + ICS 日历 + 通用 Webhook”，复杂自动化交给可选的 n8n，而不是自己造 400 个集成。
5. **技术栈建议**：Electron + electron-vite + React + shadcn/ui + Drizzle + better-sqlite3 + Vercel AI SDK + Zod。与现有原型视觉一致，后续可直接落地。

## 1. 竞品地图：四个象限

| 象限 | 代表项目 | 强项 | 缺口（我们的机会） |
|---|---|---|---|
| 团队项目管理层 | Plane、Huly、OpenProject、Vikunja、Leantime | 任务、冲刺、里程碑、甘特、团队协作 | 重、多用户、无个人产能/承诺管理；不适合“老板给我派活”的个人场景 |
| 个人执行层 | Super Productivity、open-sunsama、Sunsama（商业）、Motion（商业） | 今日计划、时间盒、计时、专注 | 缺项目组合、风险、周报、画像；对“多项目 + 被派活”支持弱 |
| AI Chief of Staff | Dex、claudia、chief-of-staff-2、DayTrail | 承诺跟踪、关系记忆、晨间简报、Markdown 工作流 | 多为 Prompt/Markdown 模板，缺结构化数据库、桌面 UX、可量化指标 |
| 本地知识库 | Obsidian、Logseq、SiYuan、AppFlowy、AFFiNE | 本地优先、双链、插件生态、AI 接入 | 缺项目管理语义、估时、风险、产能校验；需要大量插件拼装 |

**结论**：这四类都只覆盖了一部分。真正空缺的是：

> **给“既管多个项目、又被老板派活”的人用的、本地优先的、能算产能和承诺、能自动出报告和画像的个人项目工作台。**

这正好是“小鱼”的定位。

## 2. 最值得研究的 12 个项目

### 2.1 Super Productivity — 执行层最佳参考

- 仓库：`super-productivity/super-productivity`
- 数据：约 23k stars · TypeScript / Angular · **MIT**
- 是什么：待办 + 时间盒 + 计时 + 每日总结，集成 Jira、GitLab、GitHub、OpenProject。
- 可借鉴：
  - 时间盒（Timeboxing）与“今天只放这么多”的交互；
  - 计时器与任务状态联动；
  - 每日收尾总结的结构；
  - 外部 issue 同步的字段映射思路。
- 是否复用：**不建议 fork**（Angular 技术栈与我们的 React 不一致），但建议逐屏研究，必要时参考其数据模型与计时逻辑（MIT 允许）。
- 对我们的价值：直接验证了“时间盒 + 计时 + 日报”是有人用的，不用从零教育市场。

### 2.2 ActivityWatch — 画像与节奏数据的现成引擎

- 仓库：`ActivityWatch/activitywatch`
- 数据：约 19k stars · Python · **MPL-2.0**
- 是什么：跨平台自动时间追踪，记录窗口标题、AFK、浏览器活动，本地存储，隐私优先，提供 REST API。
- 可借鉴/直接集成：
  - 不自己写 OS 级窗口监听；
  - 通过 `localhost:5600` API 拉取活动片段，映射到任务/项目；
  - 自动得到“深度工作块、上下文切换、加班、周末工作、效率时段”。
- 是否复用：**作为可选伴生应用集成**，不修改其源码。MPL-2.0 是文件级 copyleft，独立进程 + API 调用对我们的闭源/自用都安全。
- 注意：需要用户额外安装 ActivityWatch；首次配置要引导，不能默认静默采集。

### 2.3 open-sunsama — 今日计划与时间块的直接竞品

- 仓库：`ShadowWalker2014/open-sunsama`
- 数据：约 109 stars · 2026-10 活跃 · 许可证 NOASSERTION（复用前必须读 LICENSE）
- 是什么：开源 Sunsama 替代，日计划、看板、时间块、专注模式，支持 Claude/ChatGPT 的 MCP 连接、REST API、Web/桌面/移动、自托管。
- 可借鉴：
  - “今日承诺”与时间块的视觉表达；
  - MCP 连接器，让 AI 直接读写任务；
  - 日历与任务的叠放方式。
- 是否复用：**参考产品设计**；代码复用前先确认许可证。它证明“AI 可调用的日计划器”是可行方向。

### 2.4 DayTrail — 本地优先的“工作记忆 + 承诺”

- 仓库：`varaprasadreddy9676/DayTrail`
- 数据：约 61 stars · 2026-10 活跃 · 许可证 NOASSERTION
- 是什么：本地优先的 AI 工作记忆，帮助回顾一天、恢复上下文、跟踪承诺、决定下一步。
- 可借鉴：
  - “承诺（commitment）”作为一等对象；
  - 一天结束时的“回溯 + 下一步”流程；
  - 本地优先的数据与隐私叙事。
- 是否复用：参考概念；许可证待确认。

### 2.5 Dex / chief-of-staff-2 / claudia — AI Chief of Staff 的三种形态

- `davekilleen/Dex`：约 500 stars · MIT · “AI Chief of Staff”个人操作系统 starter kit，无需写代码。
- `jdpolasky/chief-of-staff-2`：约 51 stars · MIT · 纯 Markdown + Obsidian + Claude Code，跟踪日历、承诺、规则，早上给简报，ADHD 友好。
- `kbanc85/claudia`：约 300 stars · 终端 AI Chief of Staff，记住关系、跟踪承诺、帮助战略思考。
- 可借鉴：
  - **晨间简报**的结构：今天必须做、承诺到期、等待他人、需要决策；
  - **承诺台账**：我答应了谁、什么时候、当前状态；
  - **关系记忆**：每个人/每个项目的偏好与历史；
  - **规则文件**：把你的工作习惯写成可执行的规则，而不是藏在脑子里。
- 是否复用：不建议直接套用（它们是 Prompt/Markdown 工作流，不是桌面应用），但这是最好的“交互与话术”参考。
- 启发：我们可以在应用里内置一个“规则/偏好”页面，让用户用自然语言定义自己的排期规则，AI 按规则执行。

### 2.6 Plane — 项目组合与风险视图参考

- 仓库：`makeplane/plane`
- 数据：约 61k stars · TypeScript · **AGPL-3.0**
- 是什么：开源 Jira/Linear/ClickUp 替代，任务、冲刺、文档、Triage。
- 可借鉴：
  - 项目健康度与周期视图；
  - 任务状态机与优先级；
  - 风险/阻塞的表达；
  - 键盘优先的交互。
- 是否复用：**不要 fork / 不要复制源码**（AGPL，分发会触发源码开放）。只做产品与信息架构参考。

### 2.7 Huly — 一体化工作台的模块化思路

- 仓库：`hcengineering/platform`
- 数据：约 28k stars · TypeScript · **EPL-2.0**
- 是什么：一体化项目管理平台（Linear + Jira + Slack + Notion + Motion 的替代）。
- 可借鉴：
  - 模块化领域模型（项目、任务、文档、聊天、HR）；
  - 多视图切换（列表/看板/时间线）；
  - 统一搜索与命令面板。
- 是否复用：EPL-2.0 是弱 copyleft，**不要复制源码到我们的产品**；参考架构即可。

### 2.8 OpenProject — 传统 PM 的完整数据模型

- 仓库：`opf/openproject`
- 数据：约 16.5k stars · Ruby · **GPL-3.0**
- 是什么：老牌开源项目管理，支持组合管理、甘特、时间追踪、预算、风险。
- 可借鉴：
  - 项目组合（Portfolio）视图；
  - 里程碑、依赖、基线；
  - 风险登记册（RAID）字段；
  - 时间与成本口径。
- 是否复用：**不要嵌入**（GPL + Rails 重架构）。把它当“PM 术语词典”。

### 2.9 NocoDB / Teable / Twenty — 自定义字段与元数据驱动

- `nocodb/nocodb`：Airtable 替代，支持自定义字段、视图、API。
- `teableio/teable`：高性能 Airtable 替代。
- `twentyhq/twenty`：开源 CRM，**metadata-driven**（自定义对象/字段/视图），非常适合参考“数据可扩展”。
- 可借鉴：
  - `custom_field_def` + `custom_field_value` 的元数据模型；
  - 字段类型系统（文本/数字/单选/多选/人员/关联/公式）；
  - 保存视图（filter/sort/group）；
  - 从表格导入时自动推断字段类型。
- 是否复用：**不嵌入**（都是重服务端应用），但数据模型可以直接借鉴。
- 关键启发：用户说“所有数据不仅仅是这几个内容，我可以根据需求集成各类数据”，那就不要把字段写死。核心实体 + 自定义字段 + 原始数据层，是必须的。

### 2.10 n8n / Activepieces — 连接器与自动化的“外包”

- `n8n-io/n8n`：约 208k stars · **Sustainable Use License（fair-code，不是 OSI 开源）**。
- `activepieces/activepieces`：约 25k stars · 许可证 NOASSERTION（含 MIT 部分）。
- 是什么：可视化自动化，几百个连接器（飞书/钉钉/邮件/表格/HTTP）。
- 可借鉴：
  - 连接器抽象：认证、触发、动作、字段映射；
  - 失败重试与运行日志；
  - “Webhook 作为通用入口”的思路。
- 是否复用：**不要把 n8n 嵌入分发给最终用户**（许可证限制 + 体积大）。更好的方式：
  - 应用内置“通用 Webhook + CSV/ICS”；
  - 高级用户可自行部署 n8n，通过 Webhook 与小鱼互通；
  - 我们提供“自动化规则”的轻量版（当…且…则…）。
- 这能省掉 80% 的连接器开发量，又不被许可证绑住。

### 2.11 Khoj / Reor — 本地 AI 记忆

- `khoj-ai/khoj`：约 37.8k stars · Python · **AGPL-3.0**，可自托管，支持文档/网页问答、定时任务、研究。
- `reorproject/reor`：约 8.5k stars · **已归档**，本地 AI 知识管理。
- 可借鉴：
  - 文档切分、向量检索、引用溯源；
  - “定时研究/自动简报”的任务编排。
- 是否复用：不直接嵌入（AGPL/已归档）。如果以后要做“项目知识库问答”，用 `sqlite-vec` + 自己的分块管线即可，个人规模足够。
- 结论：**RAG 不是 v1 的核心**。先把结构化任务/项目/报告跑通，知识库放 v2。

### 2.12 Taskwarrior / Timewarrior — 个人任务与时间的经典模型

- `GothenburgBitFactory/taskwarrior`：约 6.1k stars · **MIT**，CLI 任务管理，urgent 算法、依赖、递归任务。
- `GothenburgBitFactory/timewarrior`：约 1.7k stars · **MIT**，CLI 时间追踪与报表。
- 可借鉴：
  - Taskwarrior 的 **urgency 评分**（截止、优先级、依赖、等待、项目权重）；
  - 递归任务与依赖表达；
  - Timewarrior 的“时间区间 + 标签 + 报表”模型。
- 是否复用：不嵌入 CLI，但可以把 urgency 公式和导入格式作为参考。
- 启发：我们的“优先级分数”应该可解释，像 Taskwarrior 一样让用户看到每一项的权重。

### 不建议引入的

- **完整 PM 平台**：Plane、Huly、OpenProject、AppFlowy、AFFiNE —— 架构与许可证都不适合做桌面个人版的底座。
- **通用 Agent 框架**：LangChain/AutoGen/CrewAI —— 对“单用户、结构化任务、可复现报告”来说过重；直接 AI SDK + 少量手写编排更可控。
- **向量数据库**：Chroma/Qdrant/Weaviate —— 个人数据量用 sqlite-vec 足够，别加服务。
- **本地知识库全家桶**：Khoj/SiYuan —— v2 再考虑，别让 v1 失焦。
- **微信机器人**：Wechaty 等有封号风险，工作场景不建议作为正式集成。

## 4. 许可证风险清单

| 许可证 | 含义 | 我们的策略 |
|---|---|---|
| MIT / Apache-2.0 / BSD / ISC | 宽松，可商用、可修改 | 可直接依赖；保留版权声明 |
| MPL-2.0 | 文件级 copyleft，修改的文件需开源 | 独立进程/API 集成；不修改源码 |
| EPL-2.0 | 弱 copyleft | 不复制源码；独立调用 |
| GPL-3.0 | 强 copyleft，分发衍生作品需开源 | 不嵌入、不复制；仅参考 |
| AGPL-3.0 | 网络使用也触发开源 | 不嵌入、不复制；仅参考 |
| Sustainable Use / Fair-code | 不是 OSI 开源，商用/托管有限制 | 不作为依赖分发；仅外部可选 |
| NOASSERTION | 许可证无法自动识别 | 复用前人工读 LICENSE，必要时放弃 |

> 结论：**Plane、Huly、OpenProject、AppFlowy、AFFiNE、Logseq、SiYuan、Khoj、Vikunja、Leantime、Kimai 都只做产品参考，不复制代码。** Super Productivity（MIT）和 ActivityWatch（MPL，独立进程）是少数可以“借力”的。

## 5. 建议的拼装式架构

```text
┌─────────────────────────────────────────────────────┐
│ Electron 桌面壳                                      │
│                                                     │
│  React UI（今日 / 项目 / 报表 / 画像 / 数据集成）    │
│        │                                            │
│  Main Process                                       │
│   ├─ 领域服务：任务、项目、承诺、产能、风险          │
│   ├─ 调度器：提醒、日报、周报、备份                  │
│   ├─ AI Gateway：DeepSeek / OpenAI / Ollama          │
│   ├─ 连接器：CSV、ICS、Webhook、飞书（后续）         │
│   └─ 导出：MD / DOCX / XLSX / PDF                    │
│        │                                            │
│  SQLite（Drizzle）                                   │
│   ├─ 核心表 + custom_fields(JSON)                    │
│   ├─ source_item（原始数据，永久保留）               │
│   └─ event_log（审计/画像）                           │
└───────────────┬─────────────────────────────────────┘
                │ localhost API / webhook
     ┌──────────┴──────────┐
     │                     │
┌────▼─────────┐    ┌──────▼──────────┐
│ ActivityWatch│    │ 可选：n8n        │
│ 自动时间追踪 │    │ 复杂连接器/自动化│
└──────────────┘    └─────────────────┘
```

**为什么不是微服务？**
- 单用户桌面应用，SQLite + 单进程足够；
- 连接器、AI、报表都在本地，离线可用；
- 需要重能力（文档解析、本地模型）时，用可选 sidecar，不默认安装。

**数据扩展的关键设计（回应“数据不仅是这几个内容”）：**

```text
core entity（项目/任务/风险/人员/文档）
  + custom_field_def（实体类型、字段名、类型、选项、默认值、是否必填）
  + custom_field_value（实体 id、字段 id、值 JSON）
  + saved_view（筛选/排序/分组/列配置）
  + source_item（来源、外部 id、原始 JSON、抓取时间、映射版本）
  + connector（类型、认证、同步频率、字段映射、启用状态）
  + automation_rule（触发事件、条件、动作）
```

这样加数据源时，不需要改表结构；加字段时，不需要发版；加视图时，不需要写新页面。

## 6. 功能映射：抄什么、接什么、自己写什么

| 功能 | 最佳参考 | 决策 |
|---|---|---|
| 快速捕获 / 收件箱 | open-sunsama、Super Productivity | **自己写**（核心体验） |
| 今日排期 / 时间盒 | Super Productivity | **自己写 + 借鉴交互** |
| 计时 / 实际耗时 | Super Productivity、Timewarrior | **自己写**（简单） |
| 自动时间追踪 | ActivityWatch | **集成**（可选伴生） |
| 项目组合 / 里程碑 | Plane、OpenProject | **参考 + 轻量自研** |
| 甘特 / 依赖 | OpenProject、Plane | **v1 只做里程碑时间线** |
| 自定义字段 / 视图 | NocoDB、Twenty | **参考 + 自研轻量版** |
| AI 分类 / 估时 | 无成熟开源方案 | **自己写（核心壁垒）** |
| 日报 / 周报 | Super Productivity 的每日总结 + n8n | **自己写 facts 层 + LLM 叙述** |
| 风险分析 | OpenProject 风险登记册 | **自己写规则引擎** |
| 个人画像 | ActivityWatch + 自研指标 | **自己写** |
| 本地知识库 / RAG | Khoj、sqlite-vec | **v2 再做** |
| 连接器 | n8n | **v1 只做 CSV/ICS/Webhook；复杂交外部 n8n** |
| 模型路由 | LiteLLM / AI SDK | **AI SDK + 自定义 Provider 配置** |
| 打包 / 更新 | electron-builder | **直接用** |

## 7. 差异化机会（调研后更确定）

1. **双视角**：一键在“我的今天”和“项目组合”之间切换。现有工具要么偏团队 PM，要么偏个人待办。
2. **承诺与产能引擎**：不仅列任务，还计算“今天能不能装下”“答应老板的时间是否现实”。
3. **插单影响分析**：老板临时加活时，立即显示会挤掉什么、延期几天，并生成沟通话术。这个交互在现有开源项目里几乎看不到。
4. **事实型报告**：SQL 算 facts，LLM 只写叙述，每条结论可引用 task_id。解决“AI 周报假大空”。
5. **可解释画像**：不评分、不排名，只跟自己比，每个指标可下钻。ActivityWatch 提供原始数据，我们做解释层。
6. **本地优先 + 模型可选**：DeepSeek/OpenAI/Ollama 按项目切换，敏感数据不出本机。
7. **数据可扩展**：自定义字段 + 连接器 + 原始数据层，不被“固定几个字段”限制。

**一句话定位：**

> 给既管项目又被派活的人，一个本地优先、会算产能、能自动汇报的个人项目工作台。

## 8. 接下来建议做的 3 个技术验证（Spike）

### Spike 1：ActivityWatch 集成（0.5～1 天）

- 启动 ActivityWatch，调用 `http://localhost:5600/api/0/buckets/` 与 events API；
- 拉取最近 7 天窗口/AFK 数据；
- 生成“高效时段热力图 + 上下文切换次数”；
- 验收：不写 OS 钩子，能拿到可用的节奏数据。

### Spike 2：中文任务结构化（0.5 天）

- 用 AI SDK + Zod，把一段老板消息解析成：项目、截止、P50/P90、优先级、子任务、缺失字段；
- 测试 20 条真实消息；
- 验收：字段完整率 ≥ 90%，低置信度能正确标记“需要确认”。

### Spike 3：可扩展数据模型（1 天）

- better-sqlite3 + Drizzle 建核心表 + `custom_field_def/value` + `source_item`；
- 导入一个 Excel（字段不一致）；
- 验收：不改表结构能新增 3 个自定义字段，并能在列表/报表中使用。

> 这三个 Spike 通过后，再进入正式开发，能避免“视觉做完发现数据层不支持”的返工。

## 10. 对当前方案的影响

1. **数据模型**：在原有方案上增加 `source_item`、`custom_field_def`、`custom_field_value`、`saved_view`、`connector`、`automation_rule`。这直接回应“数据可以按需集成”。
2. **画像**：优先接 ActivityWatch，而不是自己做 OS 级监听；第一版只做“节奏/执行力/估算力”三个维度。
3. **集成**：v1 只做 3+1（CSV、ICS、Webhook、手动），把 n8n 作为高级用户的可选项。
4. **视觉**：不改方向。数据与集成页已经在原型里预留，后续把连接器卡片做成真实配置入口。
5. **开发顺序**：先做 Spike 1/2/3，再进入 Electron 开发；避免先做 UI 再返工数据层。
